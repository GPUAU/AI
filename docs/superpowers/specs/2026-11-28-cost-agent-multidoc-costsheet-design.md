# 원가 에이전트 — 부서별 문서로 원가 기준표 채우기 (자동 기입 + 담당자 확인 + 검증)

> 작성 2026-11-28 · 상태: 설계 확정 (담당자 승인) · 개정: 원가 칸은 스프링 원가 계산 항목만 (담당자 결정)
> 대상 코드: `GPUAU-AI/cost-agent` (feat/pdf-input 위), `GPUAU-FE` 원가 에이전트 화면
> 근거: 담당자 시나리오(2026-11-28), 팀 목데이터 `H100_부서별_보고서.zip`(8개 부서 PDF), 교수님 질문, 현재 코드

## 1. 왜

사업기획·프라이싱 담당자는 부서마다 견적서·청구서·명세를 받아(구매팀, 인프라운영팀, 시설운영팀, 재무회계팀, 관리회계팀, 영업팀, 자금팀, 사업기획팀) **자기 엑셀에 손으로 옮겨 적는다.** 숫자가 많아 오기입이 생기고, 잘못 옮겼는지 확인하기 어렵다.
에이전트가 **문서를 읽어 기준표(담당자 엑셀)를 채우고**, 담당자는 확인·수정만 하며, 에이전트가 **원본·부서 간·검산 대비로 검증**한다. 그 위에서 원가 계산(스프링) → 판매가 → 시장 위치.

교수님 질문 "왜 자동 기입까지 안 하냐"에 대한 설계 답:
- 값은 외부 AI로 보내지 않는다 — LLM은 가린 사본에서 위치(문서·행·열)만 답하고, 숫자는 서버 안 코드가 원본에서 꺼낸다. 그래서 자동 기입을 해도 민감정보는 나가지 않는다.
- 사람이 판단할 값이 있다 — 마진·할인율·부서 간 값이 다를 때 어느 쪽을 믿을지는 가격 책임자가 정한다. 확정은 담당자.
- 자동 기입은 틀릴 수 있다 — 그래서 칸마다 출처를 남기고, 원본 대조·부서 간 비교·검산 비교를 함께 둔다.

## 2. 목표 · 하지 않을 것 · 실패로 볼 것

- 목표
  1. 한 세션에 문서 여러 개(PDF·엑셀)를 받아 **기준표**의 칸을 채운다. 칸마다 출처(문서·쪽·행·열·원문)를 남긴다.
  2. 빈칸·충돌·저신뢰 칸을 담당자가 **한 번에 확인·수정**한다. 어느 부서도 주지 않는 칸은 담당 부서를 표시한다.
  3. 부서 간 같은 값 교차 확인, 원본 대조, 검산 문서 대비 산술 검증, 스프링 원가 항목의 빈칸 확인.
  4. 기준표로 스프링 원가 API를 부르고, 판매가·시장 위치·(기존) 승인 검토·근거서를 낸다. 기준표는 엑셀로 내려받는다.
- 하지 않을 것: **스프링 원가 계산에 없는 원가 요소**(장비 유지보수·보증, 소프트웨어 라이선스, 보험 등 — 모든 원가 요소를 아우를 수 없다고 보고 스프링 항목으로 범위를 정함, 담당자 결정), 스프링에 기준표 저장(B안, 나중), 분기 재점검, 보고서 LLM 서술, 별도 'LLM 검증 에이전트'(검증은 코드와 정답 세트로).
- 실패로 볼 것: LLM이 숫자를 만들거나 옮김 · 가린 사본 밖의 값·회사명·견적번호가 LLM에 감 · 부서 간 값이 다른데 조용히 하나를 고름 · 같은 비용을 두 문서에서 두 번 더함 · 문장 속 연간 금액을 월로 읽어 ×12 두 번.

## 3. 접근 (담당자 선택)

| 결정 | 선택 | 버린 안 |
|---|---|---|
| 여러 문서를 모으는 법 | **A. 문서마다 종류별 추출 → 칸 단위로 합치기** (청구서는 기존 분류·해석·총액 대조 그대로) | B. 모든 문서를 한 번에 LLM에 — 문서별 총액 대조·단위 해석 불가, 입력이 길어짐 |
| 기준표 위치 | **A. cost-agent 세션 데이터** (스프링에는 계산 요청만) | B. 스프링 저장 API — BE 작업·범위 증가 |
| 에이전트 성격 | 숫자 경로는 워크플로, 문서→칸 매핑·충돌·누락 대응은 에이전트(기존 LangGraph + guard) | 완전 자율 에이전트 |

## 4. 설계

### 4-1. 기준표 (`CostSheet`, 스프링 원가 API 기준)

**원가 칸** — 스프링 `/cost-simulations`의 원가 항목 그대로 (스프링에 없는 원가 요소는 다루지 않는다).

| 칸 | BE 항목 | 기간 | 주로 오는 문서 |
|---|---|---|---|
| 랙·상면 | RACK_FACILITY | 연 | 시설 청구서 |
| 임차료·공간 | RENT | 연 | 시설 청구서 |
| 전기료 | ELECTRICITY | 연 | 시설 청구서 |
| 네트워크·스토리지 | NETWORK_STORAGE | 연 | 시설 청구서 |
| 운영·유지보수 | OPERATIONS | 연 | 시설 청구서의 운영 줄 + 관리회계 '사내 인건비·판관비' (**구성 요소**로 나눠 보여 주고 합산) |
| GPU 임차 · 메모리 · 기타 | GPU · MEMORY · OTHER | 연 | 청구서 |
| 취득비 | ACQUISITION | 1회 | 구매 견적·재무회계 |
| 금융비용 | FINANCING (금리) | — | 자금팀 (가정 칸의 금리) |

- **구성 요소 합산과 충돌의 구분**: OPERATIONS처럼 서로 다른 성격의 금액(청구서 운영비, 사내 인건비·판관비)이 모이는 칸은 구성 요소별로 출처를 두고 더한다. 같은 구성 요소를 두 문서가 주면(예: 취득비를 01·04가 줌) 그때만 교차 확인·충돌 규칙을 적용한다.

**가정 칸**: GPU 모델 · GPU 수 · 감가 연수 · 유료 가동률 · 마진 방식 · 목표 마진 · 환율 · 금리 종류·연 금리 · 3·5년 할인율.

**칸 구조**: `value`, `unit`, `currency`, `period`, `status`(`filled`·`included`·`excluded`·`empty`·`conflict`), `sources: list[Source]`, `grade`(출처 등급), `candidates`(충돌 시 문서별 값), `owner`(담당 부서 — 문서가 없을 때 안내).
`Source = {doc, page, row, col, text, conf}`.

### 4-2. 문서 종류 판별 (`docs.py`)

제목·첫 줄 단어로 먼저 판별, 애매하면 가린 제목만 LLM에 묻는다.

| 종류 | 단어 | 추출 |
|---|---|---|
| **QUOTE 견적서** | 견적 | 모든 원가 줄 = 취득비. 공급가액 합계 우선(부가세 제외). GPU 모델·서버 수·장당 GPU 힌트 |
| **BILL 청구서·영수증** | 청구, 영수증, 수납, 시설비, 이용료 | 기존 파이프라인(분류·해석·총액 대조·연간화) → 원가 칸 |
| **MEMO 부서 명세** | 명세, 계획, 기준, 검토안 | 표의 `항목 | 근거 | 제출값` 줄 → 가정 칸·원가 칸 (§4-3) |
| **PLAN 검산 문서** | 검토안 + 판매가·시간당 원가 결과 | 기준표 값은 MEMO처럼 쓰고, '결과' 줄(연간 원가·시간당 원가·판매가)은 **산술 검증용**으로만 (§4-6) |

### 4-3. 칸 매핑 — 가린 사본 + 위치만 (`mapping`)

- MEMO·QUOTE: 줄의 항목명으로 칸을 정한다. 키워드 규칙이 먼저(예: 취득비, 내용연수, 유료 가동률, 계획 환율, 목표 마진, GPU 모델, 서버 구성, 사내 인건비, 판관비), 남은 줄만 LLM에 보낸다.
- LLM에 보내는 것: 기준표 칸 목록 + 가린 줄(`id`, 칸 글자, 숫자 칸은 `#NUM`, 글자 속 숫자 `#`, 회사·사업장·견적번호 가림). 받는 것: 칸마다 `(줄 id, 열 번호)` 또는 없음. **값은 코드가 원본 칸에서 읽는다.**
- **값 읽기 (`values.py`)**: `32장`·`4대`·`5년`·`70%`·`20%`·`1,009,000,000원`·`1USD=1,350KRW`·`H100 80GB`·`280,320 GPU·시간`·`약 1,885원`·`약 1.74USD` → `(숫자, 단위, 통화)`. 계산 근거 칸(`32장×365일×24시간`)보다 **제출값·결과·공급가액 열**을 우선한다.
- **표 우선, 문장은 교차 확인만**: "공급가액은 1,009,000,000원입니다", "연간 시설비는 … 96,000,000원입니다" 같은 문장 값은 기준표에 쓰지 않고 표 값과 비교만 한다 (연·월 표현을 함께 읽어 두 번 연간화 방지).
- PDF 띄어쓰기가 `\x01`로 뽑히는 글꼴: 읽을 때 공백으로 바꾼다.

### 4-4. 합치기 · 교차 확인 · 우선순위

- 같은 칸을 여러 문서가 주면: 값이 같으면(±0.5%) `filled` + 출처 여러 개(**교차 확인됨**). 다르면 `conflict` + 문서별 후보 → 담당자가 고른다. **자동으로 고르거나 더하지 않는다.**
- 파생 관계 확인: GPU 수 = 서버 수 × 장당 GPU, 연간 공급 시간 = GPU 수 × 8,760, 가동률 = 유료 시간 ÷ 공급 시간, 연간 감가 = 취득비 ÷ 연수 — 문서에 둘 다 있으면 맞는지 본다.
- 교차 확인의 범위를 화면에 밝힌다: "같은 원본(구매 견적)에서 온 값끼리의 비교라 **옮겨 적기 오류**를 잡습니다. 원본 오류는 기준선·시장 비교로 봅니다."
- 우선순위: **사내 문서 값 > 공개값** (예: 자금팀 계획 환율 1,350 > 수출입은행 1,450, 차이와 판매가 영향 표시) · 표 > 문장 · 담당자 입력 > 자동 기입.

### 4-5. 누락 · 문서가 없는 칸

- 스프링 원가 칸 중 비어 있는 것: 청구서 핵심 4개(전력·공간·네트워크·운영), 취득비, 금융비용(금리). 문서가 없으면 `empty` + 담당 부서(취득비 → 구매팀·재무회계팀, 금리 → 자금팀, 사내 인건비 → 관리회계팀, 가동률 → 영업팀)를 표시한다.
- 담당자는 `금액 입력` / `다른 칸에 포함` / `해당 없음(사유)` 중 고른다. `해당 없음`도 출처('담당자 확인')로 남는다.

### 4-6. 검증 (실행 중, 코드)

| 검증 | 내용 |
|---|---|
| 원본 대조 | 담당자가 고친 칸의 값이 그 칸 출처 원문과 다르면 표시 (오기입) |
| 부서 간 교차 확인 | §4-4 |
| 검산 문서 대비 | PLAN 문서의 연간 원가·시간당 원가·판매가와 에이전트 계산을 비교 → "산술 검증 일치/차이"로만 표시 (같은 입력의 같은 식이므로 **누락 여부는 보장하지 않음**을 함께 표시) |
| 기준선 (기존 + 추가) | 기존 상면·전력 단가, GPU당 kW, 원가 수준 + **GPU당 월 전력량**(H100 기준 대략 GPU당 월 약 900~1,500kWh, PUE 포함)이 크게 작으면 경고 |
| 시장 위치 | 기존 그대로 (범위 밖이면 담당자 결정, 승인 검토 `MARKET_OUT_KEPT`) |
| 기존 | 총액 대조, 해석 확인, 승인 검토, 자동 검증 7종 |

### 4-7. 마스킹 확장

숫자·등록된 이름에 더해 **회사명 패턴**(`○○컴퓨팅`, `(주)`, `(가상 업체)` 앞 단어, `Inc.`, `Ltd.`), **견적·영수증 번호**(`[A-Z]{2,}-\d{4,}(-\d+)?`), **사업장명**(설정 목록, 기본 `울산`) 가림. 보낸 내용은 지금처럼 세션에 공개(감사).

### 4-8. 짙은 배경 OCR

OCR 쪽 이미지의 평균 밝기가 0.45 미만(0~1)이면 반전, 이어서 자동 대비(autocontrast)를 적용한 뒤 OCR. 짙은 배경 샘플(배경 #1F2937, 글자 흰색)로 전처리 전후 글자 정확도를 잰다.

### 4-9. 화면과 결과

- 업로드: 파일 여러 개(PDF·엑셀·CSV). 문서마다 종류·쪽 수·읽은 방식(텍스트/OCR) 표시.
- **기준표 확인 카드** (기존 누락 카드 자리, 단계 이름 `누락 확인` → `기준표 확인`): 문제 있는 칸만 입력칸으로 — 빈칸(담당 부서 표시), 충돌(문서별 후보 select), 저신뢰(원문 hint), 해석 바뀐 칸. 문제가 없으면 카드 없이 통과.
- 결과 화면·근거서 첫 시트 `원가 기준표`: 칸 · 값 · 상태 · 출처(문서·쪽·행·열) · 교차 확인 수 · 담당자 수정 여부.
- API: `POST /v1/agent/sessions`가 `files`(여러 개)를 받는다. 기존 `file` 하나도 그대로 받는다.
